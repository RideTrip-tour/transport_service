# Epic 08: Наблюдаемость и надежность

## 1. Цель эпика

Сделать поведение сервиса измеримым, предсказуемым и устойчивым при сбоях внешних зависимостей.

## 2. Результат эпика

- Полный набор технических метрик.
- Структурированные логи по критичным операциям.
- Алерты на деградацию.
- Guardrails для защиты от перегрузки.

## 3. Задачи

1. Добавить метрики:
   - latency (`search/recalculate/batch`);
   - error rate;
   - cache hit ratio;
   - provider SLA.
2. Ввести корреляцию запросов (`request_id`, `trace_id`).
3. Добавить structured logging для:
   - provider calls;
   - routing;
   - batch execution.
4. Реализовать guardrails:
   - лимит размера входных данных;
   - лимит путей в routing;
   - limit на batch size.
5. Настроить алерты:
   - рост 5xx;
   - рост latency p95/p99;
   - падение cache hit ratio.
6. Документировать runbook деградации.

## 4. Декомпозиция на подзадачи

1. Определить минимальный SLA/SLO.
2. Определить дашборд MVP.
3. Описать процедуры аварийного отключения тяжелых режимов.
4. Добавить health/readiness проверки зависимостей.

## 5. Зависимости

- Вход: Epic 03, 04, 05, 06, 07.
- Выход для эпика: 9 и release readiness.

## 6. Риски и меры

1. Риск: шумные логи без пользы.
   - Мера: стандарт полей логов и sampling.
2. Риск: метрики без эксплуатационной ценности.
   - Мера: фиксировать метрики от use-case и SLO.

## 7. Критерии готовности (DoD)

1. Есть дашборды и алерты по ключевым сигналам.
2. Инциденты воспроизводимы по логам и trace-id.
3. Сервис устойчиво деградирует при частичных отказах зависимостей.

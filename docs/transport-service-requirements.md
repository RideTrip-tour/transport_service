# Transport Service Requirements

## 1. Назначение

`transport-service` рассчитывает мультимодальные маршруты между локациями с учетом даты, расписаний, пользовательских предпочтений и стоимости.

Сервис должен:
- принимать `origin_location_id`, `destination_location_id`, `date`, `preferences`;
- запрашивать доступные сегменты у внешних провайдеров;
- кэшировать результаты сегментов на 1 час;
- строить маршруты из одного или нескольких сегментов;
- рассчитывать:
  - общую стоимость;
  - общее время в пути;
  - длительность пересадок;
- возвращать несколько лучших вариантов (`top-N`);
- пересчитывать ранее сформированный маршрут;
- хранить историю поисков.

Сервис не должен заниматься:
- оплатой;
- бронированием;
- уведомлениями;
- rate limiting;
- управлением пользователями.

## 2. Границы ответственности

Взаимодействие с другими сервисами:
- `gateway`: аутентификация, авторизация, rate limit;
- `auth-service`: токены;
- `profile-service`: закладки, предпочтения, достижения;
- `location-service`: транспортные хабы;
- `notification-service` (будущий): уведомления о снижении цены.

`transport-service`:
- читает локации через API `location-service`;
- возвращает ссылку на оплату, полученную от провайдера;
- принимает команды на массовый пересчет маршрутов.

## 3. Основные сценарии

### 3.1 Поиск маршрута (онлайн)

Вход:
- `origin_location_id`
- `destination_location_id`
- `date`
- `preferences` (типы транспорта, максимальное время, бюджет и т.д.)

Процесс:
1. Получение хабов отправления/прибытия.
2. Проверка кэша сегментов (Redis).
3. Если кэша нет — запрос к внешним API.
4. Кэширование ответов (`TTL = 3600`).
5. Построение графа сегментов.
6. Поиск допустимых маршрутов с учетом расписаний и времени пересадки.
7. Сортировка: по цене, по времени, по комбинированной метрике.
8. Возврат `top-N` вариантов.

### 3.2 Пересчет сохраненного маршрута

Вход:
- `route_id`

Процесс:
- обновление сегментов у провайдеров;
- пересчет итоговой стоимости;
- возврат актуального состояния маршрута.

### 3.3 Массовый пересчет (batch)

Использование:
- cron-задача;
- внешний сервис уведомлений.

Вход:
- список маршрутов.

Особенности:
- группировка направлений для оптимизации;
- повторное использование кэшированных сегментов.

## 4. Архитектура

### 4.1 Adapter Layer

Требуется абстракция `ProviderAdapter` и реализации:
- `FlightProviderAdapter`
- `TrainProviderAdapter`
- `BusProviderAdapter`
- `FerryProviderAdapter`

Цели:
- изоляция интеграций;
- подмена провайдеров;
- упрощение тестирования;
- независимое масштабирование.

### 4.2 Routing Engine

Внутренний модуль:
- узлы графа = транспортные хабы;
- ребра графа = сегменты.

Алгоритм:
- модифицированный Dijkstra;
- или multi-criteria shortest path.

Ограничения/фильтры:
- минимальное время пересадки;
- исключение нежелательных типов транспорта;
- ограничение бюджета.

## 5. Модель данных (черновик)

### 5.1 `segments`
- `id`
- `provider`
- `transport_type`
- `origin_hub_id`
- `destination_hub_id`
- `departure_time`
- `arrival_time`
- `price`
- `currency`
- `external_id`
- `raw_payload` (`jsonb`)
- `expires_at`

### 5.2 `routes`
- `id`
- `origin_location_id`
- `destination_location_id`
- `date`
- `total_price`
- `total_duration`
- `segments_snapshot` (`jsonb`)
- `created_at`
- `recalculated_at`

### 5.3 `search_history`
- `id`
- `user_id`
- `origin_location_id`
- `destination_location_id`
- `date`
- `preferences`
- `created_at`

Redis key:
- `segment:{origin}:{dest}:{date}`
- `TTL: 3600`

## 6. API контракт

- `POST /routes/search`
- `POST /routes/{id}/recalculate`
- `POST /routes/batch-recalculate`

### 6.1 `POST /routes/search`

Request:
- `origin_id`
- `destination_id`
- `date`
- `preferences`

Response:
- `list[RouteDTO]`

## 7. Этапы реализации

1. Базовый скелет:
   - FastAPI;
   - PostgreSQL схема;
   - Redis;
   - структура адаптеров.
2. Интеграция одного провайдера:
   - `FlightAdapter`;
   - кэш сегментов;
   - прямые маршруты.
3. Маршруты с пересадками:
   - граф;
   - алгоритм поиска;
   - фильтрация пересадок.
4. Мультимодальность:
   - поддержка `transport_type`;
   - единая модель сегмента.
5. Batch пересчет:
   - endpoint;
   - группировка направлений.
6. Оптимизация:
   - индексы PostgreSQL;
   - профилирование алгоритма;
   - конкурентные запросы к провайдерам.

## 8. Архитектурные риски

1. Комбинаторный взрыв маршрутов:
   - ограничить глубину (например, до 3 пересадок).
2. Перегрузка внешних API:
   - агрессивное кэширование и группировка batch.
3. Сложность multi-criteria оптимизации:
   - сначала weighted score, затем Pareto frontier.
4. Актуальность цен:
   - обязательный пересчет перед финальной оплатой.

## 9. Стратегические рекомендации

1. Выделить `routing engine` в независимый модуль.
2. Использовать `jsonb` для snapshot сегментов.
3. Добавить `route_version` для безопасного пересчета.
4. Подготовить архитектуру к:
   - динамическому ценообразованию;
   - ML-ранжированию;
   - кэшированию готовых маршрутов.
